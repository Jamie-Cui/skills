# 密码实现审查流程

## 适用范围

本流程适用于密码原语与构造、加密、签名、密钥交换、密钥管理协议、ZK 电路与
证明系统、门限密码、MPC，以及应用系统中的密码使用。

本流程负责把安全需求映射到协议、实现和集成证据，并构造形式化验证之前的安全
归约图。新算法的理论安全性、完整证明有效性和新颖性由
`crypto-research-reviewer` 负责；其结论可以作为本报告的外部证据。

只审查，不修改代码，不生成可直接应用的补丁，也不在同一独立审查中混入修复。

## 建立审查目标

用户指定文件、函数或算法时，检查这些目标以及验证安全性质所需的依赖。对于仓库级
请求，先发现完整密码表面，包括：

- 密码依赖、算法名、协议名、标准、论文和测试向量；
- 密钥、nonce、IV、随机性、transcript、证明、签名、密文和 commitment 类型；
- 解析、编码、验证、密钥生成、加解密、签名、证明和协议入口；
- vendored、fork、生成、FFI、硬件描述和平台特定实现；
- 调用方如何处理返回值、错误、部分输出和持久化状态。

为每个独立算法或协议建立目标记录：

```markdown
### 目标：{名称}

- 识别置信度：高 / 中 / 低
- 来源：标准化 / 自定义 / 未确定
- 用途与安全目标：...
- 权威依据与精确版本：...
- 实现入口：...
- 外部接口和调用方：...
- 威胁模型假设：...
- 对应根节点：...
```

多个独立子系统无法在一次审查中可靠覆盖时，仍需先给出完整清单，再按安全影响和
可达性推荐深审顺序。不得把样本结论推广到未审查目标。

## 解析权威依据

按以下原则选择证据，而不是使用与领域无关的固定机构排序：

1. 用户明确指定的规范、论文、协议版本或安全 profile；
2. 实现明确声明遵循的规范及其主管机构发布的勘误和测试向量；
3. 适用于该用途的正式标准、官方参考实现和当前安全指南；
4. 仓库设计文档与明确安全模型；
5. 互操作行为和测试；
6. 代码注释与推断出的实现意图。

核对发布状态、版本、勘误、撤回、废止和替代文件。草案只能作为临时依据；除非用户
或实现明确指定，不得把符合草案表述为符合最终标准。

若代码给出无歧义的公开论文引用，可以从权威来源获取并分析，无需再次确认。若算法
映射是根据名称或行为推断的，应建立 `NEEDS_HUMAN_REVIEW` 节点，在等待确认期间继续
进行不依赖该映射的实现分析。

## 标准化算法与自定义算法

### 标准化算法

分开评估：

- **声明版本符合性**：实现是否符合它声称的精确标准版本；
- **当前安全状态**：算法、参数和 profile 在当前指南中是否仍允许或推荐。

旧实现符合旧标准不等于它符合当前标准；当前弃用也不自动证明旧实现违反其声明标准。
两项结论应形成不同节点。

规范性措辞确定符合性，不直接确定严重性。违反 `MUST` 或 `MUST NOT` 可以建立
不符合事实，但严重性取决于安全、正确性、互操作性和可达性影响。

### 自定义算法

先建立以下节点：算法语法、安全目标、攻击模型、计算假设、参数依据、证明来源和测试
向量。缺少独立规范或精确契约时，不能判定算法安全，应把未决理论问题交给
`crypto-research-reviewer`，并在当前图中标为 `NEEDS_HUMAN_REVIEW`。

本 skill 可以判断代码是否忠实实现已确认的算法契约，但不得用“未找到攻击”替代
理论安全结论。

## 三个审查层次

每个目标都应在以下三个层次建立节点；确实不适用时记录理由。

### 算法与协议安全

检查实现所依赖的算法安全结论是否有明确来源、适用于当前参数和协议组合，并检查：

- 安全定义、攻击模型和信任边界；
- 参数、安全强度、已知攻击和当前允许状态；
- domain separation、transcript binding、降级和重放防护；
- 协议组合是否满足理论结论的前置条件；
- 理论证明或外部评审结论是否映射到实际变体。

理论结论缺失、过期或不适用时建立人工审核节点，不在本流程中自行宣称证明成立。

### 实现正确性

根据适用规范检查：

- 算术域、约简、溢出、符号、边界、字节序和转换规则；
- 规范编码、解码、长度、拒绝行为和尾随数据；
- 群、曲线、域、点、子群和单位元验证；
- 参数选择与强制执行；
- 随机数、确定性派生、nonce、IV、计数器唯一性和耗尽；
- 密钥生成、导入、导出、状态转换和秘密生命周期；
- 验证返回值、错误传播、部分输出和 fail-open 路径；
- 协议消息、参与方身份、顺序、重放状态、轮次和门限检查；
- ZK 约束完整性、公开输入与 witness 绑定、transcript、challenge、setup 和拒绝；
- 重复实现、优化实现、生成代码、FFI 和参考实现之间的一致性；
- secret-dependent branch、secret-dependent memory access、可变时延操作和
  所依赖的 constant-time API 合约。

### 使用与集成安全

检查：

- 原语、构造、模式和参数是否满足应用安全目标；
- 密钥、nonce、IV、salt、label、context 和 associated data 的生成、作用域、
  分离与持久化；
- 跨协议 domain separation；
- 降级、重放、回滚、密钥轮换和版本协商；
- 调用方是否强制验证结果，是否暴露未认证或部分明文；
- 错误是否形成 padding、validity 或 decryption oracle；
- 信任边界和密钥所有权；
- 外部 API 的错误、状态和生命周期契约。

## 可执行证据

在能够实质增强节点判断时，运行安全、本地、只读或临时验证：

- 现有构建和测试；
- 官方测试向量和负向量；
- 有界的性质、fuzz、差分和互操作测试；
- 适用的静态分析和语言原生检查；
- 对疑似错误的最小复现实验。

记录命令、工具版本、输入类、持续时间或界限、退出状态和观察结果。区分直接观察到的
失败、理论风险和未执行假设。临时 harness 和下载资料放在仓库外；未经授权不得安装
依赖、运行长期 fuzz、访问生产环境、使用真实秘密或要求硬件探测。

源码审查可以评估明显的 secret-dependent 控制流和 API 合约，但不能代替编译器、
微架构、功耗、电磁或故障注入验证。此类覆盖缺口必须成为人工审核节点或明确排除项。

## 依赖和安全公告

- 普通外部密码依赖：确认解析后的版本、配置、API 合约、算法选择和密码相关公告；
  除非用户要求，不审计其全部上游实现。
- 未修改的 vendored 依赖：检查来源、版本、可得的完整性证据和本地集成边界。
- fork、本地移植或修改过的 vendored 实现：把受影响路径当作本地代码审查。
- 只有在版本和配置适用性确定后，才能断言公告影响当前目标；否则建立待确认节点。
- 不把本流程扩展为通用依赖漏洞扫描。

## 问题严重性与置信度

失败节点派生 finding 时，按实际影响和可达性评定：

- `Critical`：在现实前置条件下击败主要安全性质或造成灾难性妥协；
- `High`：实质破坏安全性质或广泛违反关键协议不变量；
- `Medium`：条件受限但需要实质整改的弱点；
- `Low`：安全影响有限或局部正确性、互操作性问题。

置信度与严重性分开：

- `High`：映射、触发、证据和影响已直接验证或强有力确立；
- `Medium`：问题证据充分，但仍有一个实质前提未验证；
- `Low`：问题值得记录，但仍需大量验证。

证据不足本身不构成 finding；它应形成 `NEEDS_HUMAN_REVIEW` 节点。

## 报告与交接

最终报告必须符合 `report-schema.md`，并以 `security-reduction-method.md` 的规则
构图和传播状态。整改简报按图的依赖顺序排列失败节点：先处理会阻断多个上层需求的
共享节点，再处理局部叶节点。

交接给实现流程的是 `required_outcome` 和 `acceptance_check`，不是替换代码。交接给
形式化验证流程的是明确命题、前置条件、状态模型、不变量、模型边界和代码映射。
