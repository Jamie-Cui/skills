# 安全归约方法

## 目的

安全归约图是一个有向无环图。它回答两个方向的问题：

- 向下：某个顶层安全需求依赖哪些更具体的安全义务？
- 向上：底层证据、反例或未决问题如何影响顶层结论？

图不是代码调用图、模块依赖图或检查清单。节点必须是可以判断真假的安全陈述，
边必须说明子陈述为何支撑父陈述。

## 根安全需求

每个根节点必须包含：

- 受保护的资产或安全目标；
- 攻击者能力；
- 系统允许的前置条件；
- 被禁止的结果；
- 时间、会话、参与方和部署边界；
- 与规范或需求文档的对应位置。

例如，“签名是安全的”不是合格根需求；“在攻击者可自适应请求选定消息签名、
但不能读取私钥的条件下，攻击者不能为未查询消息生成被验证接口接受的签名”
才具有可继续分解的语义。

如果用户只给出模糊目标，先根据接口、调用方和文档形成候选根需求，并把推断标记
为 `NEEDS_HUMAN_REVIEW`。只有不同解释会显著改变审查路径时才要求用户先确认。

## 节点类型

每个节点必须选择一个 `kind`：

- `security_requirement`：顶层或系统级安全需求；
- `security_property`：机密性、完整性、真实性、不可伪造性等性质；
- `reduction_obligation`：父命题到子命题的归约是否有效；
- `assumption`：计算、信任、环境或部署假设；
- `protocol_obligation`：协议设计、状态机、消息或 transcript 层面的义务；
- `implementation_obligation`：规范到代码的对应、算术、解析、验证或状态实现义务；
- `integration_obligation`：调用、密钥生命周期、持久化、错误处理和跨协议组合义务；
- `evidence_obligation`：测试向量、差分测试、静态分析或其他证据必须满足的条件；
- `formalization_target`：边界明确、准备交给形式化验证的命题。

节点类型不决定状态，也不代替具体陈述。

## 分解顺序

优先沿以下层次分解，但允许根据目标省略不适用层次：

1. 系统安全需求；
2. 安全性质、攻击游戏或理想功能；
3. 威胁模型和信任边界；
4. 算法与协议安全义务；
5. 参数、计算假设和外部组件假设；
6. 规范到实现的对应义务；
7. 集成、状态和生命周期义务；
8. 可执行证据、人工判断问题或形式化验证命题。

每次分解必须满足：

- 子节点比父节点更具体；
- 子节点仍是安全陈述，而不是文件名、函数名或待办动作；
- `decomposition.rationale` 解释子节点组合为何足以支撑父节点；
- 每个子节点使用 `relation` 说明它与父节点的关系；
- 未证明充分性的分解本身必须由 `reduction_obligation` 节点承载。

合法的 `relation` 为：

- `REFINES`：把抽象性质细化为具体义务；
- `ASSUMES`：引入父节点依赖的外部假设；
- `IMPLEMENTS`：实现行为对应规范、协议或抽象模型；
- `PRESERVES`：变换、优化或组合保持某项性质；
- `VALIDATES`：子节点检查父节点所需的具体行为。

不得使用 `EVIDENCED_BY` 连接节点；证据通过 `evidence_refs` 引用证据登记表，
避免把“存在证据”和“安全命题成立”混为一谈。

## 组合逻辑

非叶节点必须声明 `decomposition.operator`：

- `AND`：所有子节点都是父节点成立的必要条件；
- `OR`：子节点是经过论证的替代路径，任一路径成立即可支撑父节点。

使用 `OR` 时，`decomposition.rationale` 必须说明为什么这些路径确实可替代，以及
选择某条路径不会绕过其他独立必要条件。混合逻辑应引入中间节点，不能在一个节点
中写隐含的复杂布尔表达式。

叶节点使用 `LEAF`，且不得包含子节点。

## 停止分解

只有满足以下一项时，节点才可成为叶节点：

### `machine_checkable`

存在边界明确的测试、向量、分析器或验证程序。节点必须写明输入类、执行方法、
预期结果和失败判据。工具成功退出本身不是安全证据，除非该退出状态正是验收条件。

### `human_judgment`

问题已经缩小为指定领域专家能够回答的有限问题。节点状态必须是
`NEEDS_HUMAN_REVIEW`，并填写审核问题、所需专业能力和所需材料。

### `external_assumption`

节点依赖审查范围外的组件、信任根、平台或组织保证。只有在该假设被威胁模型明确
接受且存在适用证据时才能判 `PASS`；否则判 `NEEDS_HUMAN_REVIEW`。已知假设不成立
时判 `FAIL`。

### `formalization_boundary`

节点已被表达为可交给形式化工具或证明人员的命题，包含前置条件、状态模型、输入、
不变量、结论和模型边界。尚未完成证明时通常为 `NEEDS_HUMAN_REVIEW`；已有适用且
验证过的证明证据时才可判 `PASS`。

### `counterexample`

存在可复现反例、违反规范的执行路径或不满足的必要条件。节点必须判 `FAIL`，并记录
反例、触发条件和影响。不得继续无意义分解来稀释失败结论。

不得因为层数、时间、上下文长度或“看起来足够具体”而停止。资源限制只能形成覆盖
说明和 `NEEDS_HUMAN_REVIEW` 节点。

## 三态判断

### `PASS`

只有同时满足以下条件才能使用：

- 节点陈述明确；
- 验收条件明确；
- 引用证据直接适用于目标版本、配置和威胁模型；
- 证据满足验收条件；
- 子节点状态按组合逻辑允许父节点通过。

`PASS` 表示“在本报告边界内得到支持”，不是普遍安全证明。

### `FAIL`

用于以下情况：

- 有明确反例；
- 违反适用规范或实现契约；
- 必要安全义务不成立；
- 状态传播规则要求父节点失败。

严重性由影响和可达性决定，不能仅由规范中的 `MUST` 或节点层级决定。

### `NEEDS_HUMAN_REVIEW`

用于以下情况：

- 需要密码学、平台、编译器、硬件或部署专家判断；
- 权威依据、威胁模型、版本映射或运行环境不明确；
- 现有证据不足以通过，也没有证据证明失败；
- 所需证明、实验或外部确认尚未完成；
- 子节点状态传播后仍有未决义务。

直接判定为该状态的节点必须包含一个可回答的问题，不得只写“需要更多审核”。
仅因子节点传播而得到该状态的祖先节点不重复创建人工任务，但必须在判断理由中列出
阻塞它的直接子节点。

## 状态传播

先评估叶节点，再按逆拓扑顺序传播：

| 节点逻辑 | 子节点状态 | 父节点状态 |
|---|---|---|
| `AND` | 任一 `FAIL` | `FAIL` |
| `AND` | 全部 `PASS` | `PASS` |
| `AND` | 其他组合 | `NEEDS_HUMAN_REVIEW` |
| `OR` | 任一合格替代路径 `PASS` | `PASS` |
| `OR` | 全部 `FAIL` | `FAIL` |
| `OR` | 其他组合 | `NEEDS_HUMAN_REVIEW` |

父节点可因自身直接反例而变为 `FAIL`，即使子节点尚未完成。父节点不得通过人工叙述
覆盖由子节点机械推导出的 `FAIL` 或 `NEEDS_HUMAN_REVIEW`。如果传播结果不符合分析者
的安全直觉，应修改错误的分解结构，而不是修改状态规则。

## 从图派生结果

- 每个直接判定为 `FAIL` 的节点必须生成或关联一个问题条目；多个同源失败可以合并，
  但必须保留所有关联节点 ID。仅由子节点传播失败的祖先不重复生成 finding。
- 每个直接判定为 `NEEDS_HUMAN_REVIEW` 的节点必须出现在人工审核队列中。仅由
  子节点传播未决状态的祖先不重复进入队列。
- 适合形式化验证的节点应明确标记，并提供命题、前置条件、模型边界和代码位置。
- 所有问题、人工任务和形式化目标必须能够向上追踪到至少一个根安全需求。
